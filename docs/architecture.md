# Веб-каталогизатор: план новой архитектуры

Цель — клиент-серверное приложение: SPA на Vue с базовой аутентификацией (без регистрации) и
мощным расширенным поиском книг. Документ фиксирует, что уже есть в FLibrary, что из этого
переиспользуемо, и описывает целевую архитектуру.

## 0. Принятые решения

| Что                 | Решение                                                                                                                 |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Архитектура сервера | **Гибрид** (вариант C, п. 3): свой API + существующий C++ `opds` как внутренний content-service                         |
| Стек API            | **TypeScript + Fastify**                                                                                                |
| Масштаб             | **Несколько пользователей, сотни тысяч книг** — per-user данные полноценные, keyset-пагинация и кэш фасетов обязательны |
| Расположение кода   | **Новый отдельный репозиторий**; форк `books` остаётся только для правок в C++-сервере                                  |
| Контракт API        | **REST + OpenAPI** (GraphQL рассмотрен и отклонён, см. п. 0.1)                                                          |

Что из этого следует для приоритетов:

- Сотни тысяч книг → пагинация, кэш фасетов и **дисковый** кэш обложек нужны уже в первой
  фазе, а не «потом». Существующий `CoverCache` в C++ живёт в памяти с TTL 1 минута — для
  веб-витрины с ленивой загрузкой сеток обложек этого мало.
- Несколько пользователей → `user_id` во всех пользовательских таблицах с самого начала;
  ретрофитить это больно.
- Отдельный репозиторий → контракт между клиентом и API должен быть формальным (OpenAPI +
  генерируемый TS-клиент), потому что «просто посмотреть в соседний файл» уже не выйдет.
- Внешний поисковый движок в стартовый скоуп **не** берём: FTS5 на сотнях тысяч записей
  справляется, а контракт поиска спрятан за своим API — Meilisearch подключается позже без
  правок клиента.

### 0.1 Почему не GraphQL

GraphQL здесь выглядит уместно (каталог — это граф: книга → авторы → их книги → серия;
keyset-курсоры красиво ложатся на Relay-connections; разные представления списка хотят разные
подмножества полей), но три довода перевесили:

1. **Главная фича хуже типизируется.** Поисковый запрос — рекурсивное дерево предикатов.
   Рекурсия во входных типах GraphQL допустима, но union/`oneOf` для inputs в стабильной спеке
   нет. Узел «либо предикат по полю, либо группа AND/OR/NOT» пришлось бы описать одним
   input-типом со всеми полями опциональными и валидацией «ровно один вариант» в рантайме.
   JSON Schema описывает это точно и валидирует до кода.
2. **N+1 на SQLite.** Список из 50 книг с авторами и жанрами в REST — один SQL с
   `GROUP_CONCAT`. В GraphQL резолверы полей провоцируют запрос на книгу; без dataloader-батчинга
   это 150 запросов на страницу, и батчинг надо писать и поддерживать.
3. **Единого API всё равно не выйдет.** Обложки, fb2, zip и конвертеры через GraphQL не отдать —
   бинарные ручки остаются REST в любом случае.

Чего мы при этом **не** теряем: HTTP-кэширование поиска. Дерево предикатов едет в теле, то есть
это `POST` и в REST-варианте; кэшируются в обоих случаях только обложки (`GET`).

Если понадобится обход графа в стиле GraphQL, разумный шаг — добавить его для каталога и
навигации, оставив поиск на `POST /search` с JSON Schema; гибридность контракта из-за
бинарников у нас уже есть.

## 1. Что уже есть (проверено по коду)

FLibrary — это **не только десктоп**. В репозитории уже живёт полноценный сервер и SPA.

### 1.1 Сервер: `src/home/tool/opds` — отдельный бинарник `opds`

Приложение на Qt 6 HttpServer (`Server.cpp`), собирается как самостоятельный `app`-таргет и
линкуется с десктопной библиотекой `logic` — то есть переиспользует всю доменную логику
(коллекции, БД, извлечение книг, аннотации, фильтры).

Запускается автономно, коллекцию может создать сам:

```
opds --name <коллекция> --database <db> --archives <архивы> [--additional <дир>] [--inpx <inpx>]
```

Осторожно: на **существующей** коллекции эти аргументы пересоздают её пустой (проверено на
2.6.6). Для запуска уже готовой коллекции аргументы не нужны — путь берётся из QSettings.

- Настройки читает из QSettings (общие с десктопом): `opds/host`, `opds/port` (по умолчанию
  12791), `opds/Authentication`, флаги включения каждого «лица» сервера.
- Управляется десктопом через `IOpdsController` (Start/Stop/Restart) и локальный сокет
  (`QLocalServer`), умеет сам себя перезапускать после автообновления коллекции.
- `QGuiApplication` (нужен для работы с картинками) — на headless-сервере потребуется
  `QT_QPA_PLATFORM=offscreen`.

### 1.2 Три «лица» одного сервера

| Путь                                                                                     | Что отдаёт                                                                                                   |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `/opds/*`                                                                                | OPDS-каталог (Atom XML) для читалок: навигация по авторам/сериям/жанрам, поиск, постраничность по 25 записей |
| `/web/*`                                                                                 | Простой server-rendered HTML-интерфейс                                                                       |
| `/` + `/assets/*`                                                                        | React-SPA (`src/ext/ReactApp`, отдельный репозиторий-сабмодуль)                                              |
| `/main/getBooks/*`                                                                       | JSON-API для этой SPA                                                                                        |
| `/Images/covers/<id>`, `/Images/fb2/<id>`, `/Images/fb2compact/<id>`, `/Images/zip/<id>` | обложка, книга (с восстановлением картинок и без), книга в zip                                               |

Важно: React-SPA собирается **вне** C++-сборки, а её бандл коммитится в репозиторий как
`resources/website/assets/index.{js,css}.bin` и вшивается в бинарник через `opds.qrc` (имена
файлов с хешами Vite прописаны в qrc руками). При старте сервер сначала ищет файлы на диске
рядом с бинарником (`<appdir>/website/...`), и только потом берёт вшитые — то есть подменить
фронтенд без пересборки C++ **можно**.

### 1.3 Текущий JSON-API (то, на что сейчас опирается фронт)

`getConfig`, `getSearchStats`, `getSearchTitles`, `getSearchAuthors`, `getSearchSeries`,
`getSearchAuthorBooks`, `getSearchSeriesBooks`, `getBookForm`.

Модель поиска простая: один параметр `search` (или `selectedGroupID`), три оси результатов —
книги/авторы/серии, плюс `getSearchStats` для счётчиков. Строка запроса разбивается по
пробелам, к каждому слову приписывается `*` → префиксный FTS-поиск с неявным AND
(`PrepareSearchTerms`).

### 1.4 База: SQLite, схема из `src/home/inpx/resources/data/CreateCollection.json`

Таблицы: `Books`, `Authors` + `Author_List`, `Series` + `Series_List`, `Genres` + `Genre_List`,
`Keywords` + `Keyword_List`, `Languages`, `Folders` (архивы), `Annotations`, `Reviews`,
`Compilations`, `Updates`, `Inpx`, `Settings` и пользовательские `Books_User`, `Groups_User` +
`Groups_List_User`, `Searches_User`, `Export_List_User`.

FTS5 поверх контентных таблиц (`content=`, `content_rowid=`):

```
Books_Search        (Title)
Authors_Search      (LastName, FirstName, MiddleName)
Series_Search       (SeriesTitle)
Annotations_Search  (Text)
Compilations_Search (Title)
```

Представления `Books_View` / `Groups_List_User_View` создаются миграцией, а
`Books_View_Opds` — сервером на старте (`util/BookView.cpp`), причём его текст **зависит от
настроек**: скрывать ли удалённые книги и применять ли пользовательский фильтр
(`Flags & 2` у авторов/серий/жанров/ключевых слов + фильтр по языкам).

Оси навигации, которые умеет десктоп (`NAVIGATION_MODE_ITEMS_X_MACRO`): Authors, Series,
Genres, PublishYear, Keywords, Updates, Archives, Languages, Groups, Search (сохранённые
поиски), Reviews, AlreadyRead, AllBooks.

### 1.5 Файлы книг

Книги лежат внутри zip-архивов: `Folders.FolderTitle` — имя архива, `Books.FileName` — имя
файла внутри. Сервер распаковывает на лету (`Zip` поверх `7z.so`/bit7z), умеет восстанавливать
картинки внутри fb2, отдавать «компактную» версию без картинок, кэшировать обложки в памяти
(`CoverCache`, TTL 1 минута) и прогонять книгу через **внешние конвертеры**, настраиваемые в
`Preferences/opds/converters` (fb2 → epub/mobi и т.п.).

Это самая дорогая в переписывании часть: zip/7z, fb2-парсинг, восстановление картинок,
извлечение обложек, djvu/pdf/mobi — всё уже работает на C++ и обкатано.

### 1.6 Аутентификация — уже есть, но частичная

`Server.cpp` умеет HTTP Basic: ожидаемое значение — **солёный хеш одной пары логин:пароль** в
настройке `opds/Authentication`; пользователей и регистрации нет. Три чекера: raw, base64 и
`Basic <base64>`. Если настройка пуста — доступ открыт.

Что важно знать до проектирования:

- Проверка авторизации навешена только на `/`, `/opds/*`, `/web/*`.
  **`/main/getBooks/*` и `/Images/*` не защищены вообще** — то есть весь JSON-API и скачивание
  книг сейчас доступны без пароля.
- В `getSearchAuthorBooks` / `getSearchSeriesBooks` параметры `selectedItemID` и
  `selectedGroupID` подставляются в SQL конкатенацией (`QString::arg`), а не биндингом.
  Соединение с БД read-only, но это всё равно SQL-инъекция в неаутентифицированной ручке.
  Чинить это надо в любом варианте (и, по-хорошему, отдельным PR в upstream).

### 1.7 Ограничения, которые упираются прямо в нашу задачу

1. **Нет пагинации в JSON-API.** `getSearchTitles`/`getSearchAuthors`/`getSearchSeries`
   выбирают весь результат и склеивают в один JSON-массив. На коллекции в сотни тысяч книг
   запрос вида «всё по языку ru» положит и сервер, и браузер. OPDS-ветка страницы умеет,
   JSON — нет.
2. **Поиск без морфологии.** FTS5-таблицы созданы без `tokenize=`, то есть дефолтный
   `unicode61`: регистр и диакритика — да, стемминг русского — нет. «Стругацкие» не найдёт
   «Стругацкого». Префиксный `*` частично спасает, но не для падежных окончаний.
3. **Один пользователь.** Все `*_User`-таблицы (оценки, группы, сохранённые поиски, прочитанное)
   не имеют владельца — это данные единственного локального пользователя.
4. **Схема БД принадлежит FLibrary.** Импорт из inpx, миграции (`UpdateCollection.json`),
   `CollectionCleaner` умеет делать `rebuild` FTS-индексов. Всё, что мы допишем **в саму
   коллекцию**, может быть перетёрто при обновлении коллекции или миграции.
5. **Поиск только по 5 полям.** Год, язык, рейтинг, размер, формат, жанры, ключевые слова —
   в FTS не входят, ими можно только фильтровать SQL-условиями.

## 2. Что переиспользуем, а что пишем с нуля

| Переиспользуем как есть                                       | Пишем заново                                                                             |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Импорт inpx → SQLite + автообновление коллекции               | Весь API-контракт для веба (пагинация, расширенный поиск, фасеты)                        |
| Схему БД и FTS-индексы (как read-only источник)               | Аутентификацию и пользователей                                                           |
| Распаковку книг, восстановление картинок, обложки, конвертеры | Клиент на Vue                                                                            |
| Десктоп FLibrary как инструмент админа коллекции              | Пользовательские данные (избранное, прочитанное, сохранённые поиски) — в своём хранилище |

Ключевой вывод: **источник данных и работа с файлами уже готовы и стоят дорого**; переписывать
их — самая большая и самая бессмысленная часть работы. Новое — это API поиска, аутентификация и
клиент.

## 3. Варианты по серверу (выбран C)

Раздел оставлен как запись обоснования выбора.

### Вариант A — расширять существующий C++/Qt-сервер

Добавить в `src/home/tool/opds` новый роут-набор `/api/v1/*`: пагинация, расширенный поиск,
авторизация на всех ручках. Vue-бандл кладётся вместо React (`resources/website`).

- **Плюсы:** один процесс, один деплой; нулевое дублирование логики; прямой доступ к
  `logic`-библиотеке (аннотации, фильтры, конвертеры) без IPC; всё в одном репозитории.
- **Минусы:** каждая правка API — это C++ (Qt HttpServer, DI на Hypodermic, PIMPL) и полная
  сборка с Qt + Conan (часы, десятки ГБ). При фронтенд-компетенции итерации по API станут
  узким местом. Многопользовательская авторизация и своя таблица юзеров в C++ — заметная работа.
  И это правки в чужом upstream, которые придётся тащить как форк или продавливать в PR.

### Вариант B — полностью новый сервер, C++ выбросить

Свой сервер (TypeScript / Go / Python) читает ту же SQLite и сам распаковывает книги.

- **Плюсы:** полный контроль, один язык с фронтом (если TS), быстрые итерации, свободная
  схема для юзеров и их данных.
- **Минусы:** придётся переписать всё из п. 1.5 — zip/7z, fb2 с восстановлением картинок,
  извлечение обложек, конвертеры, mobi/djvu/pdf. Плюс аккуратно воспроизвести семантику
  «скрытых» и «удалённых» книг (`Books_View_Opds` + флаги фильтров), иначе выдача будет
  расходиться с десктопом. Реалистично это не «поднять API», а несколько месяцев.

### Вариант C — гибрид: свой API + C++ как content-service ← **выбран**

```
        браузер
           │  HTTPS
     ┌─────▼──────┐
     │  Caddy /   │  TLS, статика Vue, единый origin
     │  nginx     │
     └──┬─────┬───┘
        │     │ /api/*
        │  ┌──▼────────────────────────┐
        │  │ API (TypeScript, Fastify) │  ← вся новая логика
        │  │  • auth, сессии, юзеры    │
        │  │  • расширенный поиск      │  ATTACH ─┐
        │  │  • пагинация, фасеты      │         │
        │  │  • пользовательские данные│         │
        │  └──┬────────────────┬───────┘         │
        │     │ read-only      │ proxy           │
        │  ┌──▼──────────┐  ┌──▼──────────────┐  │
        │  │ collection  │  │ FLibrary opds   │  │
        │  │ .db (SQLite)│  │ (C++), localhost│  │
        │  └─────────────┘  │  • обложки      │  │
        │         ▲         │  • fb2 / zip    │  │
        │         │         │  • конвертеры   │  │
        │  ┌──────┴──────┐  └────────┬────────┘  │
        │  │ FLibrary    │           │           │
        │  │ desktop /   │      архивы книг      │
        │  │ inpx import │      (том с fs)       │
        │  └─────────────┘                       │
        │  ┌──────────────────────────────┐      │
        └──┤ app.db — юзеры, избранное,   ├──────┘
           │ сохранённые поиски, индексы  │
           └──────────────────────────────┘
```

Разделение ответственности:

- **C++ `opds`** остаётся внутренним сервисом (слушает только localhost) и делает то, что умеет
  лучше всех: отдаёт бинарь книги, обложку, конвертирует форматы. OPDS-фасад можно оставить
  включённым для читалок, `/web` и React — выключить настройками.
- **API на TypeScript** — единственная точка входа для клиента: авторизация, поиск, метаданные,
  а бинарные запросы стримит из C++ (или отдаёт через `X-Accel-Redirect`, если фронт-прокси
  nginx).
- **Коллекционная БД — строго read-only.** Всё своё (пользователи, их данные, дополнительные
  поисковые индексы) — в отдельном `app.db`, который подключается к тому же соединению через
  `ATTACH`. Тогда JOIN между «своим» и «коллекционным» остаётся одним SQL-запросом, а
  переимпорт коллекции ничего у нас не ломает.

Почему это лучший вариант именно здесь: вся работа, которую вы будете делать руками и часто,
оказывается на TypeScript рядом с Vue; вся работа, которую трогать не хочется, остаётся в
готовом C++ и правится только при необходимости.

**Компромисс варианта C:** два процесса вместо одного и лишний прокси-хоп на скачивании книги;
плюс контракт с C++-сервером (`/Images/*`) становится внутренним API, за который надо следить
при обновлении upstream. Это цена, которую я считаю оправданной.

## 4. Ключевые технические решения

### 4.1 Морфология поиска — решить в первую очередь

Это то, от чего зависит, будет поиск «мощным» или просто «есть».

| Подход                      | Как                                                                                     | Плюсы / минусы                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Префиксный FTS (как сейчас) | `терм*`                                                                                 | Дёшево, уже работает. Не берёт падежи: «войну и мир» → не найдёт «Война и мир»                           |
| Триграммный индекс          | FTS5 `tokenize='trigram'` (SQLite ≥ 3.34, в проекте 3.51) в **своём** `app.db`          | Полноценный подстроковый поиск и опечатки-tolerant; индекс крупнее, релевантность хуже                   |
| Стемминг на стороне API     | Нормализация запроса и индекса (`natasha`/`snowball`-порт, или свой словарь) в `app.db` | Лучшее качество для русского; нужен собственный индекс и его пересборка при обновлении коллекции         |
| Внешний движок              | Meilisearch / Typesense / OpenSearch                                                    | Морфология, опечатки, фасеты, релевантность «из коробки»; +сервис в деплое, +индексация 100k+ книг, +RAM |
| Гибрид                      | FTS5 для «быстро и точно», внешний движок для «умного» поиска                           | Максимум качества, максимум сложности                                                                    |

**Решение:** свой FTS-индекс в `app.db`, собираемый индексатором из коллекции. В одну
виртуальную таблицу сводим title + ФИО авторов + серию + ключевые слова + аннотацию, в двух
вариантах токенизации:

```sql
-- релевантность и префиксный поиск
CREATE VIRTUAL TABLE books_fts USING fts5(
    title, authors, series, keywords, annotation,
    tokenize = "unicode61 remove_diacritics 2"
);
-- подстрочный поиск и устойчивость к опечаткам/окончаниям
CREATE VIRTUAL TABLE books_trgm USING fts5(text, tokenize = "trigram");
```

Индексатор — отдельный процесс (или воркер в API), который:

1. определяет, изменилась ли коллекция: `max(UpdateID)` в `Books`, число записей и mtime файла
   БД (записывается в `index_state`);
2. читает коллекцию батчами через тот же `Books_View`-эквивалент, что и поиск (чтобы скрытые и
   удалённые книги не попадали в индекс);
3. пишет в новые таблицы, затем атомарно переключает их (`ALTER TABLE ... RENAME`) —
   поиск во время переиндексации продолжает работать на старом индексе.

Полная сборка на сотнях тысяч книг — минуты; запускается по событию обновления коллекции и по
расписанию. Если качества не хватит, Meilisearch подключается как деталь реализации за тем же
контрактом — без изменений в клиенте. Именно поэтому поиск с самого начала прячется за
собственным API.

### 4.2 Пагинация — обязательна, и лучше keyset

`LIMIT/OFFSET` на глубоких страницах по 100k+ строкам деградирует. Для стабильного порядка —
keyset-пагинация по составному курсору `(<ключ сортировки>, BookID)`, курсор отдаём клиенту
base64-строкой. Для UI «страница 1..N» всё равно нужен `total` — считать его отдельным
`count(*)` по тому же WHERE и кэшировать по хешу запроса.

### 4.3 Фасеты — сделано

Счётчики по языкам, форматам, жанрам, годам, рейтингу, авторам и сериям: `GROUP BY` по
отфильтрованному множеству, топ-20 значений (год и рейтинг — до 200), кэш в `app.db` по
хешу запроса. Реализовано в `src/search/facets.ts` и `src/search/runFacets.ts`,
обоснование и замеры — в `docs/decisions.md`, п. 10.

Главное отличие от первоначального наброска: фасет считается не по тому же фильтру, что
и выдача. Предикаты по его собственному полю снимаются, иначе фасет схлопывается в одно
выбранное значение. Из-за этого множества у фасетов разные, и совпадающие приходится
материализовать во временную таблицу, чтобы не считать одно и то же по нескольку раз.

Наличие обложки в фасеты не входит по той же причине, по которой не работает предикат
`hasCover`: в коллекции этого признака нет.

### 4.3.1 Кэш обложек

На сотнях тысяч книг витрина с сеткой обложек — основной источник нагрузки: каждая обложка
означает распаковку архива и разбор fb2 в C++. Поэтому в API — свой **дисковый** кэш:
`cache/covers/<bookId>.<size>.webp`, две размерности (thumb ~200px для списков, full для
карточки), запись после первого запроса, отдача с `ETag`/`Cache-Control: immutable`
(обложка книги не меняется), опциональный фоновый прогрев для популярных выборок.
Плейсхолдер отдаём сразу, если книга без обложки, чтобы не дёргать C++ повторно — факт
«обложки нет» тоже кэшируем.

### 4.4 Аутентификация

Требование — базовая, без регистрации. Практично так:

- Пользователи задаются конфигом/CLI (`users.yaml` или таблица в `app.db`, пароли — argon2id).
- Клиент логинится один раз (`POST /api/v1/auth/login`, Basic или JSON) → сервер ставит
  **httpOnly Secure SameSite=Lax cookie** с сессией. Дальше Basic-заголовок не гоняется.
  Причина: чистый HTTP Basic шлёт пароль в каждом запросе, не имеет logout и плохо дружит с
  SPA-роутингом.
- Для читалок (OPDS) оставляем **именно HTTP Basic** — они другого не умеют.
- Обязательно: закрыть авторизацией `/api/*` **и** бинарные ручки. Публичные обложки — если
  сознательно решим.
- C++-сервер после этого слушает только `127.0.0.1` и в интернет не смотрит.

### 4.5 Пользовательские данные

В `app.db`, с `user_id`: избранное, прочитанное, оценки, сохранённые поиски, история.
Синхронизировать их обратно в `*_User`-таблицы коллекции **не нужно** — это путь к конфликтам с
десктопом. Если понадобится импорт того, что уже накоплено в десктопе — разовая миграция.

### 4.6 Деплой

`docker compose` на одной Linux-машине: `caddy` (TLS + статика Vue) → `api` (Node) → `opds`
(C++). Библиотека (`collection.db` + архивы) — каталог с хоста, примонтированный ro; `app.db`
и кэш обложек — именованные тома там же. C++-контейнер собирается из официальной портативной
сборки релиза; headless — не `offscreen` (в сборке такого плагина нет), а `wayland` плюс
weston с headless-бэкендом. Сетевых хранилищ раскладка не поддерживает (решение 12).
Обновление коллекции — десктопом на машине с библиотекой.

Как это разворачивается, чем проверяется и на какие грабли C++-сервера мы наступили —
[docs/deploy.md](deploy.md).

## 5. Модель расширенного поиска

Главная фича продукта, поэтому проектируем её как **явный контракт**, а не набор
query-параметров.

Запрос — дерево предикатов (AND/OR/NOT), сериализуется в JSON и в компактную строку для URL
(чтобы поиск можно было отправить ссылкой):

```jsonc
{
  "op": "and",
  "nodes": [
    { "field": "author", "op": "match", "value": "стругацкий" },
    { "field": "year", "op": "range", "from": 1960, "to": 1990 },
    { "field": "lang", "op": "in", "values": ["ru"] },
    // Код коллекции, а не код FB2: «001.003» — «Социально-психологическая фантастика».
    { "field": "genre", "op": "in", "values": ["001.003"], "includeChildren": true },
    { "field": "libRate", "op": "gte", "value": 4 },
    { "op": "not", "nodes": [{ "field": "deleted", "op": "eq", "value": true }] },
  ],
  "sort": [{ "field": "relevance", "dir": "desc" }],
  "cursor": null,
  "limit": 50,
  "facets": ["lang", "genre", "year", "ext"],
}
```

Поля, доступные из схемы (см. п. 1.4):

| Группа             | Поля                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------- |
| Полнотекстовые     | `title`, `author`, `series`, `annotation`, `keyword`, `compilation`                       |
| Точные / диапазоны | `year`, `lang`, `libRate`, `userRate`, `size`, `ext`, `updateDate`, `seqNumber`           |
| Таксономии         | `genre` (дерево через `ParentCode`), `keyword`, `archive` (`Folders`), `author`, `series` |
| Пользовательские   | `favorite`, `read`, `group`, `hasReview`, `myRate`                                        |
| Служебные          | `deleted`, `hasCover`, `hasAnnotation`                                                    |

Операторы: `match` (FTS), `phrase`, `prefix`, `eq`, `in`, `range`, `gte`/`lte`, `exists`,
`empty`. Сортировки: релевантность (`bm25()`), год, название, автор, рейтинг, размер, дата
добавления, номер в серии.

На сервере это компилируется в параметризованный SQL: CTE с FTS-`MATCH` для текстовых узлов,
пересечения/объединения `BookID` для логических операторов, финальный JOIN на представление
книг + keyset-условие. **Все литералы — только через биндинг** (см. п. 1.6 — как раз то, чего
сейчас нет).

UI: конструктор запроса (строки «поле — оператор — значение», группы AND/OR), рядом «простая»
строка поиска, которая разворачивается в то же дерево. Сохранённые поиски — это просто
сохранённый JSON запроса в `app.db`.

## 7. Клиент на Vue

Стек: **Vue 3 + TypeScript + Vite**, Pinia (состояние), Vue Router, TanStack Query
(кэш и инвалидация серверных данных), Tailwind + один компонентный набор (PrimeVue — сильные
таблицы и виртуальный скролл; или shadcn-vue, если хочется полного контроля над вёрсткой),
`vue-i18n` (ru/en/uk — переводы уже есть в десктопе), Vitest + Playwright.

Экраны:

1. **Поиск** — конструктор запроса + фасетная панель + результаты (виртуальный скролл, ленивые
   обложки, переключение таблица/карточки/компактный список). Запрос живёт **в URL** — поиском
   можно поделиться, его можно сохранить.
2. **Карточка книги** — метаданные, аннотация, обложка, серия с навигацией «предыдущая/следующая»,
   кнопки скачивания в доступных форматах.
3. **Читалка fb2** — в React-версии fb2 парсится в браузере (`fast-xml-parser`); тот же приём
   годится, но лучше вынести парсинг в web worker.
4. **Автор / серия / жанр** — витрины со своим поиском внутри.
5. **Мои книги** — избранное, прочитанное, сохранённые поиски.
6. **Логин** — форма, роутер-гард, редирект.

Отдельно: скелетоны и debounce на поиске, «сохранить как поиск» одним действием, клавиатурная
навигация по результатам, PWA/офлайн-кэш — по желанию, ближе к концу.

### 7.1 Что из этого сделано

Верхнее меню: **Поиск · Авторы · Жанры · Языки**.

- **Поиск** (`/search`) — раздельные поля названия и автора, язык и жанр списками (жанр —
  деревом, с числом книг по поддереву), год ползунком-диапазоном, панель уточнения по
  фасетам. Запрос целиком лежит в URL, включая страницу и сортировку. Ссылки со старой
  формы (`?q=&in=`) продолжают открываться — на это есть тест.
  Уточнения новый поиск не сбрасывает: найдя автора, дальше ищут его же книги. Поэтому
  выбранное значение остаётся видимым в панели, даже когда под него не попало ни одной
  книги, — иначе снять его было бы нечем. Жанр из панели складывается с жанром формы по
  «и» и живёт в своём параметре URL (`?genre=…&refine=…`): в одном списке уточнение молча
  расширяло бы выдачу.
- **Авторы / Жанры / Языки** (`/authors/:id?`, `/genres/:code?`, `/languages/:code?`) —
  боковой справочник и выдача. Своих ручек выдачи не заводят: это тот же `POST /search`
  с одним предикатом. Выбранный элемент — часть пути, поэтому «назад», «вперёд» и
  отправленная ссылка работают без нашего участия. Поиск в справочнике авторов идёт с
  любого места фамилии и с начала имени и отчества (`SearchName` в коллекции — это только
  фамилия, остальное достаётся из её FTS-таблицы), а запрос отстаёт от ввода: подстрока —
  это скан справочника.
- **Выдача** (общая для поиска и разделов) — 20 книг на странице, размер переключается и
  живёт в URL. Обложки грузятся по три и только те, что доехали до экрана, на остальных
  крутится индикатор: страница выдачи целиком не помещается в очередь C++-сервера, и без
  этого её хвост оборачивался заглушками (см. `docs/decisions.md`, п. 13).
- **Карточка книги** — метаданные списком определений, каждое значение ссылка на поиск с
  этим фильтром (`/search?author=…`, `?genre=…`, `?lang=…`), а не в раздел справочника: из
  карточки хочется увидеть похожие книги и тут же сузить запрос дальше. Аннотация,
  содержание, отзывы. Часть полей приходит не из коллекции (см. 7.2) и появляется по
  готовности; чего нет — того и в карточке нет, пустых разделов не рисуем.

- **Узкий экран** — с 960px раскладка в одну колонку, с 600px обложка в карточке книги
  уходит наверх, а не отжимает текст в сантиметр. Колонки сетки объявлены `minmax(0, 1fr)`,
  и это не украшательство: у обычного `1fr` минимальная ширина равна самому длинному
  неразрывному содержимому колонки — длинное название серии в панели уточнения растягивало
  всю страницу, и на телефоне приложение оказывалось шире экрана. Длинные подписи режет
  многоточие (полное значение — в `title`), длинные «слова» вроде имён файлов переносятся.

  В одну колонку справочник разделов стоит **над** выдачей, и из этого следует остальное.
  Он больше не залипает у верхнего края: `position: sticky` во всю высоту экрана
  закрывал собой выдачу, до которой прокручивали. После выбора он сворачивается в
  заголовок с кнопкой («Выбрать автора»), а экран уезжает к книгам — иначе выбранное
  оказывается за несколькими экранами списка. Туда же уводит «Найти»: над выдачей стоят
  форма, сортировка и панель уточнения. Листание — прокруткой к началу списка, кнопки
  не меньше 44px (палец — не курсор), номеров страниц в пагинаторе три, а не пять: с
  пятью он разваливался на три строки. Размер страницы вынесен из пагинатора в шапку
  выдачи, где он один на оба пагинатора.

- **Тема** — по умолчанию системная (`prefers-color-scheme`), переключатель в шапке
  пишет выбор в `localStorage`, и он главнее системы. Пока выбора не было, приложение
  следует за системой на лету. Класс на `<html>` ставится до монтирования (`main.ts`),
  иначе тёмная тема мигает светлой на первом кадре.

Не сделано из перечисленного выше: читалка, «мои книги», сохранённые поиски,
конструктор сложных запросов, i18n (интерфейс только русский).

### 7.2 Данные помимо коллекционной БД

Издателя, ISBN, язык оригинала, переводчиков, содержание и объём текста inpx в коллекцию
не переносит — их читает разбор fb2 (`GET /books/{id}/details`). Файл при этом достаётся
через C++-сервер: распаковку архивов мы не переписываем. Разбор кэшируется на диске —
иначе каждое открытие карточки занимало бы очередь C++-сервера, размером с число ядер.

Аннотация из файла работает запасным вариантом: таблицу `Annotations` заполняет inpx, и
только с флагом `LoadAnnotations`. Пустая она — штатное состояние коллекции, поэтому нет
аннотации — нет и раздела: объяснение про `LoadAnnotations` иначе стояло бы на каждой
карточке подряд.

Отзывы читателей (`GET /books/{id}/reviews`) лежат в 7z-архивах `ADDITIONAL_DIR/reviews`;
имя записи внутри архива — `FolderTitle#FileNameExt`. Не настроено — пустой список.

Обе ручки необязательные: их отсутствие убирает поля, но не ломает карточку.

## 8. Этапы

**Фаза 0. Решения и контракт (без кода).**
Выбрать вариант сервера, стек API, модель аутентификации, стратегию морфологии; зафиксировать
OpenAPI и JSON-схему поискового дерева; решить, где живёт код (см. п. 10).
_Результат:_ спека, по которой фронт и бэк можно делать параллельно.

**Фаза 0.5. Данные для разработки.**
Нужна реальная коллекция (inpx + архивы) — это десятки гигабайт. Поэтому: генератор
синтетической коллекции (N тысяч книг, правдоподобные авторы/серии/жанры, маленькие fb2) +
готовый `collection.db`, чтобы фронтенд разрабатывался без библиотеки на диске.
_Результат:_ `docker compose up` поднимает стек с тестовыми данными.

**Фаза 1. Каркас: чтение и просмотр.**
API: аутентификация, `/search` с простым текстовым запросом и **пагинацией**, карточка книги,
проксирование обложек и скачивания. Vue: логин, список результатов, карточка, скачивание.
_Результат:_ работающий вертикальный срез, книгу можно найти и скачать.

**Фаза 2. Расширенный поиск.**
Дерево предикатов, фасеты со счётчиками, сортировки, подсказки, keyset-пагинация, сохранённые
поиски. UI-конструктор запроса, состояние в URL.
_Результат:_ заявленная главная фича.

**Фаза 3. Пользователи и их данные.**
Избранное, прочитанное, оценки, история; `app.db`-схема, миграции; провижининг пользователей.

**Фаза 4. Доводка.**
Читалка fb2, конвертеры форматов, i18n, PWA, метрики и логи, продовый деплой за TLS.

**Параллельно, независимо от выбранного варианта:** починить в C++-сервере авторизацию на
`/main/getBooks/*` и `/Images/*` и биндинг параметров в двух ручках (п. 1.6) — это отдельный
небольшой PR в upstream, полезный всем.

| Риск                                                           | Что делаем                                                                                |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Схема коллекции меняется в upstream (миграции, `rebuild` FTS)  | Читаем только через свой слой доступа; свои данные — в `app.db`; тест на схему при старте |

## 10. Новый репозиторий

Монорепо на pnpm workspaces — клиент, API и общий контракт в одном месте, но независимо от

```
flibrary-web/
  packages/
    contract/        OpenAPI-спека + JSON-схема поискового дерева + сгенерированные TS-типы
```

Правки в C++-сервере (закрыть авторизацией `/main/getBooks/*` и `/Images/*`, биндинг параметров

## 11. Бэклог первой фазы (детально)

Контракт и инфраструктура:

1. `contract`: OpenAPI для эндпоинтов фазы 1 + JSON-схема запроса поиска; генерация TS-типов.
2. `fixtures`: генератор коллекции (~50k книг, правдоподобные авторы/серии/жанры/аннотации,

   упирается в отсутствие данных, а бэкенд — в отсутствие нагрузки.
3. `deploy`: `docker compose` с тремя сервисами (caddy, api, opds), тома для БД и архивов,
   `QT_QPA_PLATFORM=offscreen` для C++.

API:

4. Слой доступа к БД: read-only соединение с `collection.db`, `ATTACH` `app.db`, миграции

7. `POST /search` — пока только текстовый предикат + сортировки + **keyset-пагинация**.
8. `GET /books/:id` — карточка (авторы, жанры, серия + номер, аннотация, доступные форматы).
9. Прокси в C++: `/books/:id/cover` с дисковым кэшем и двумя размерами, `/books/:id/content`

10. Индексатор: первая версия — полная сборка `books_fts`, запуск командой.

Клиент:

11. Каркас: Vite + TS + Pinia + Router + TanStack Query + UI-набор, генерируемый API-клиент.
12. Логин и роутер-гард.
13. Экран результатов: виртуальный скролл, ленивые обложки, простая строка поиска, состояние

## 13. Бэклог производительности

Аудит по коду: где в проекте тратятся память и CPU и что с этим делать. Дешёвые приёмы
были выбраны сразу (материализация `hits`, кэш агрегатов, дисковый кэш обложек,
keyset-пагинация); этот раздел — про то, что оставалось после них.

Пункты 13.2, 13.4 и 13.5 закрыты и помечены ниже **сделано** вместе с замерами: список
дороже без истории, чем с ней, — иначе следующий заход начнётся с тех же гипотез. Осталось
два пункта: дисковый кэш обложек (13.5) и пул read-воркеров (13.3).

Цифры — замеры на синтетической коллекции в 50 000 книг (`pnpm fixtures -- --books=50000`),
все на одной машине до и после правки; экстраполяции на реальный объём помечены как
экстраполяции. С замерами из чужих прогонов сравнивать их нельзя, только между собой.

### 13.1 Самое дорогое сейчас

| Процесс                  | Что доминирует                                          | Состояние                           |
| ------------------------ | ------------------------------------------------------- | ----------------------------------- |
| `opds` (C++ + weston)    | RAM: Qt Gui + композитор — плата за старт, не за работу | Оставляем: инвариант 5              |
| `api`, запрос с фасетами | CPU: `GROUP BY` по всему множеству                      | Сделано, п. 13.2                    |
| `reindex`                | CPU: стеммер на каждом слове; диск: два индекса разом   | Сделано, п. 13.4                    |
| `pnpm fixtures`          | RSS: JSZip держит весь архив в памяти                   | Частично, п. 13.5                   |
| argon2 при логине        | 19 МиБ на проверку — намеренный memory-hard параметр    | Не трогаем: это защита, а не расход |

### 13.2 Фасеты и `total` — сделано

Было: и счётчики, и `total` считались внутри `POST /search`. Пользователь ждал панель
уточнения, чтобы увидеть выдачу, а каждая следующая страница пересчитывала цифры, которые
от страницы не зависят вообще.

Стало: `POST /search/facets` — отдельная операция контракта, отдающая и счётчики, и `total`
(`packages/contract/openapi.yaml`, `src/routes/search.ts`). У `POST /search` остался флаг
`withTotal`, по умолчанию выключенный: это по-прежнему второй полный проход по множеству,
просто теперь за него надо попросить явно. `total` кэшируется тем же `query_cache`, что и
счётчики, — ключ не зависит ни от страницы, ни от сортировки.

Клиент (`useSearchState.ts`) строит из одной формы два запроса, и в запросе счётчиков нет
ни сортировки, ни страницы: при листании его ключ не меняется, поэтому на сервер он не
уходит вовсе.

| Запрос                          | Было (всё одним) | Стало `/search` | Стало `/search/facets` |
| ------------------------------- | ---------------- | --------------- | ---------------------- |
| «показать всё», первая страница | 186 мс           | 27 мс           | 142 мс, из кэша 1 мс   |
| «показать всё», листание        | 46 мс            | 27 мс           | не запрашивается       |
| текстовый запрос                | 13 мс            | 3 мс            | 8 мс, из кэша 1 мс     |

Суммарной работы стало меньше не в разы, а по месту: выдача больше не ждёт счётчиков,
а листание их не пересчитывает.

### 13.3 Потолок конкурентности API

`better-sqlite3` синхронный, соединение на чтение одно: пока считается «показать всё»
с фасетами, весь процесс стоит (линейно по объёму коллекции — на миллионе это секунды).
Снимается только пулом воркеров (`worker_threads`) со своими read-соединениями: коллекция
открыта READONLY, `app.db` в WAL, несколько читателей допустимы. Работа заметная, и после
13.2 она стала менее срочной: самый дорогой запрос ушёл с пути выдачи, а его результат
кэшируется. Делать, когда упрёмся в конкурентность, а не раньше.

Дешёвая часть — сделано: на read-соединении выставлены `cache_size = -65536` (64 МиБ,
отдельной строкой для `main` и для присоединённой коллекции — у каждой схемы свой пейджер)
и `temp_store = MEMORY` ради временной таблицы `hits` (`src/db/index.ts`). На фикстуре в
50 000 книг разницы не видно: файл целиком в кэше ОС. Правка рассчитана на коллекцию в
гигабайты, где дефолтные 2 МБ дают промах на каждом джойне со справочниками. `mmap_size`
пока не включён: раньше причина была в SMB-раскладке (случайные чтения по сети — больное
место), теперь коллекция всегда на локальном диске, так что это открытый вариант —
включать по замерам на настоящей коллекции, а не вслепую.

### 13.4 Индексатор — сделано

1. **Кэш стемминга.** `stemRussian` мемоизирован (`src/search/stemmer.ts`): словарь каталога
   меньше числа слов в нём, а разбор окончаний до этого повторялся на каждое вхождение —
   1,2 млн вызовов на фикстуре. Полная сборка индекса: 3,1 с → 2,2 с. Размер кэша ограничен,
   при переполнении он сбрасывается целиком: на реальной коллекции уникальных токенов
   заметно больше, чем на синтетической, а живёт кэш и в процессе API, не только в
   индексаторе.
2. **Инкрементальная переиндексация.** `reindex` без `--force` дописывает только новые
   поставки (`UpdateID` больше прежнего максимума) прямо в рабочие таблицы: 500 книг
   доиндексируются меньше чем за 0,1 с против 2,2 с полной сборки, и пика в два индекса
   на диске больше нет. Условие безопасности — число книг до прежней границы должно
   совпасть с тем, что было при сборке: не совпало, значит в старой части что-то пропало,
   и нужна полная сборка. Правку существующей книги доиндексация не видит (`UpdateID`
   ставит импорт, а не редактирование) — на это есть `--force`; подробности в
   `src/indexer/README.md`.
3. **Объём триграммного индекса.** Аннотации из него уже исключены; следующий кандидат —
   `keywords`, если размер `app.db` станет проблемой. Не делалось.

### 13.5 Память вне горячего пути

- **`fixtures` — сделано, но эффект меньше ожидавшегося.** Архив пишется потоком
  (`generateNodeStream` в `createWriteStream`) вместо `generateAsync({type:'nodebuffer'})`,
  то есть готовый архив больше не материализуется вторым буфером. Пик RSS на
  `--books=50000`: 483 → 436 МБ при архивах по 5 000 книг и 1227 → 1023 МБ, если сложить
  все книги в один архив. Остаток — записи текущего архива, которые JSZip держит целиком,
  плюс мусор от сборки самих fb2. Отсюда поправка к прежней оценке: пик задаётся
  `--per-archive`, а не `--books`, и до OOM дело не доходит — под ограничением кучи в
  192 МБ генератор доезжает до конца и до правки, и после. Радикальное лечение — потоковый
  zip-writer вместо JSZip; ради генератора фикстур это не окупается.
- **Обложки вычитываются целиком в `Buffer.concat`** (`src/routes/books.ts`). Для thumb это
  норма, для `size=full` при сетке с холодным кэшем — N мегабайтных буферов одновременно.
  Ограничить конкурентность обращений к content-service. Не делалось.
- **Дисковый кэш обложек растёт без вытеснения:** ни LRU, ни квоты. На большой коллекции это
  гигабайты, о которых сейчас никто не помнит. Не делалось.

## 14. Бэклог безопасности

Аудит по коду, сделан после того, как заработали поиск и деплой. Ждал бэклога
производительности (п. 13), потому что часть 14.4 закрывалась теми же правками; п. 13
сделан в основном объёме, так что **это следующая работа**.

### 14.1 Модель угроз

Без неё список находок превращается в чек-лист «сделайте всё», а половина пунктов этому
проекту не нужна.

- Один аккаунт на семью и друзей, пароль передаётся из рук в руки. Регистрации нет,
  ролей нет, разграничения между людьми нет и не планируется.
- Приложение смотрит в интернет через nginx proxy manager, TLS терминируется на нём.
- **Что защищаем:** саму библиотеку — она не должна быть доступна и видна посторонним;
  и работоспособность сервиса — упавший api означает, что читать нечего.
- **Что вне модели:** злоумышленник с валидной кукой. Разграничение прав, неотказуемость,
  аудит скачиваний, защита от инсайдера — всё это не имеет смысла при одном аккаунте.
  Не путать «не сделано» с «сделано плохо»: это осознанный отказ.

Отсюда порядок: сначала периметр (что доступно без куки) и устойчивость к нагрузке,
потом гигиена аутентификации, и никогда — многопользовательские механизмы.

### 14.2 Что проверено и держится

Чтобы при следующем заходе не проверять заново:

- **Инвариант 2 соблюдён.** Пройдены все места сборки SQL (`src/search/compile.ts`,
  `search/facets.ts`, `routes/search.ts`, `routes/relations.ts`, `routes/catalog.ts`):
  в текст запроса интерполируются только серверные константы — `COLLECTION`, выражения
  `FACET_SPECS`, операторы из белого списка, имена колонок `INDEX_COLUMNS`. Поля предикатов
  и фасетов ограничены enum'ами контракта до попадания в `Record`-lookup. Инъекции нет.
- Коллекция физически read-only (инвариант 1), проверено записью в `coll.*`.
- argon2id; `timingSafeEqual` на подписи куки; проверка пароля от dummy-хеша при
  несуществующем логине (`routes/auth.ts`) — по времени ответа логин не угадывается.
- Ни одного `v-html`/`innerHTML` во фронте; Vue экранирует по умолчанию.
- Ввод в FTS5 обезврежен кавычками (`search/fts.ts`), `LIKE` — с `ESCAPE '\'`.
- Ключ кэша фасетов включает `userId` (`search/runFacets.ts`) — счётчики не перетекают
  между пользователями. При одном аккаунте неважно, но правильно.
- `Content-Disposition` от C++-сервера перекладывается в `filename*` через
  percent-encoding (`routes/books.ts`) — CRLF-инъекция в заголовок невозможна.
- Секретов в репозитории нет, `.env` в `.gitignore` и `.dockerignore`.

### 14.3 Периметр: что отдаётся без аутентификации

Главный пункт при нашей модели угроз — ровно то, что «скрывает либу от посторонних глаз».

Сейчас без куки доступны только `POST /auth/login`, `POST /auth/logout` и `GET /health`.
Остальное закрыто хуком `onRequest` в `src/auth/plugin.ts` (инвариант 4). Оставшееся:

1. **`/health` отдаёт число книг и версию схемы коллекции** и проксируется наружу. Это
   разведданные о том, что за сервером стоит и насколько он интересен. Свести ответ к
   `{status:'ok'}`, а подробности — за аутентификацию.
2. **Обложки не проверяют существование книги и `hideDeleted`** (`routes/books.ts`),
   в отличие от соседней `/content`, которая проверяет. Следствий два: обложки скрытых
   книг отдаются, и любой `bookId` уходит в C++-сервер и создаёт на диске файл-маркер
   `.missing` — по файлу на идентификатор, без ограничений. Забивание диска перебором.

### 14.4 Устойчивость: DoS одним запросом

Здесь прямая связка с п. 13.3: `better-sqlite3` синхронный, read-соединение одно, поэтому
любой дорогой запрос останавливает весь процесс. То, что в п. 13 — вопрос отзывчивости,
здесь — вопрос доступности.

1. **Rate limit есть ровно на одной ручке.** В `src/server.ts` плагин зарегистрирован с
   `global: false`, и `rateLimit` в конфиге маршрута стоит только у `/auth/login`.
   Всё остальное не ограничено ничем.
2. **Дорогие запросы доступны любому вошедшему.** Каждый `NOT` компилируется в
   `SELECT BookID FROM coll.Books EXCEPT ...`, то есть полный скан; `offset` разрешён
   до 5 000 000 (комментарий в `search/compile.ts` сам признаёт ~4 с на последнюю
   страницу); фасеты считают всё совпавшее множество. Пара параллельных таких запросов
   кладёт сервис. Правки из 13.2 часть поверхности сняли — `/search` больше не считает
   ни счётчиков, ни `total`, а результат `/search/facets` кэшируется, — но саму
   возможность попросить дорогое они не убирают: `POST /search/facets` с каждым новым
   фильтром считается заново. Нужен лимит.
3. **Глубина дерева предикатов не ограничена.** `SearchNode` → `SearchGroup.nodes` →
   `SearchNode` рекурсивна; `maxItems: 32` ограничивает ширину, но не вложенность.
   Проверено на сгенерированной схеме: глубина 1000 (23 КБ) валидируется штатно,
   глубина 2000 (46 КБ при `bodyLimit` в 256 КБ) роняет Ajv в
   `RangeError: Maximum call stack size exceeded`. Рекурсия без границы есть и дальше —
   в `compileNode` и `mentionsDeleted`. Лечится проверкой глубины перед компиляцией.
4. **Скачивание книг не ограничено ничем** — при утёкшей куке библиотека выкачивается
   в один поток.

### 14.5 Прокси и кука: специфика nginx proxy manager

Ставим за NPM, а не за Caddy из `deploy/docker-compose.yml`, — отсюда три вещи, которые
надо развести явно, иначе они ломаются молча.

1. **`trustProxy: true` в проде обнуляет rate limit.** `src/server.ts` включает доверие
   всем прокси, а `proxy-addr` при «доверять всем» берёт крайний левый адрес
   `X-Forwarded-For` — он целиком под контролем клиента. Значит `request.ip` подделывается
   заголовком, и единственный существующий лимит (10 попыток входа в минуту) обходится
   сменой заголовка на каждом запросе. При одном аккаунте это единственная дверь в
   библиотеку, поэтому чинить обязательно: доверять фиксированному числу хопов
   (`trustProxy: 1`, а при связке NPM → caddy → api — 2) или списку адресов, но не всем.
2. **Кука `Secure` и доступ по HTTP.** `COOKIE_SECURE=true` (стоит в compose) — правильно:
   TLS терминируется на NPM, до api идёт HTTP, и без этого флага кука ушла бы в открытую.
   Грабли: если открыть приложение мимо NPM — по IP и порту, по HTTP, — браузер молча
   выбросит `Secure`-куку, и вход будет «не работать» без единой ошибки в логах. Записать
   в `docs/deploy.md`; при локальной проверке `COOKIE_SECURE=false`.
3. **Заголовки безопасности переезжают в NPM.** Сейчас `nosniff`, `X-Frame-Options` и
   `Referrer-Policy` живут в `deploy/Caddyfile` — если Caddy из схемы уходит, они
   пропадают вместе с ним. Плюс их и так не хватает: нет `Content-Security-Policy`
   (сдерживать будущий XSS нечем) и нет HSTS. Проще всего задать всё в NPM в разделе
   Advanced у прокси-хоста и там же держать.

### 14.6 Гигиена аутентификации

При одном аккаунте это не срочно, но пункты дешёвые.

1. **Сессии не чистятся.** `deleteExpiredSessions` определена в `src/auth/sessions.ts` и
   не вызывается нигде — таблица растёт вечно. Вызывать при старте и по таймеру.
2. **Смена пароля не отзывает сессии.** `setPassword` меняет хеш, но выданные куки живут
   свои 30 дней. Единственный сценарий, где это важно, — «пароль ушёл не тому», а он
   при передаче из рук в руки как раз и вероятен. Чистить `sessions` в той же транзакции.
3. **Логин попадает в лог при неудачном входе** (`routes/auth.ts`). Классика: человек
   промахнулся полем и ввёл пароль в «логин» — пароль оказывается в логах открытым текстом.
4. **Контейнеры работают от root** — ни `USER` в Dockerfile'ах, ни `user:` в compose.
   Дёшево закрыть, а RCE в любой зависимости иначе сразу даёт root.
5. **Open redirect в форме входа:** `router.push(route.query.redirect)` без проверки
   (`views/LoginView.vue`). Браузер, скорее всего, отобьёт протокол-относительный
   `//evil.com` на `pushState`, но полагаться на это не стоит — проверять
   `startsWith('/') && !startsWith('//')`.

### 14.7 Чего сознательно не делаем

Чтобы это не всплывало в следующем аудите как «упущение»:

- **CSRF-защиты нет.** Сегодня она и не нужна: `SameSite=Lax` плюс требование
  `application/json` (кросс-сайт форма такой Content-Type не отправит) закрывают
  практические сценарии, а из POST-ручек есть только вход и выход. **Пересмотреть, когда
  появятся ручки пользовательских данных** (п. 4.5): `PUT /books/:id/favorite` уже будет
  менять состояние, и вот тогда защита нужна.
- Разграничение прав, роли, аудит скачиваний, «выйти на всех устройствах», ротация
  сессий — всё это про многопользовательский сценарий, которого нет.
- 2FA, политика паролей, блокировка аккаунта — при одном аккаунте с длинным паролем
  дают неудобство без выигрыша.

### 14.8 Порядок

1. `trustProxy` фиксированным числом хопов (14.5.1) — одна строка, чинит единственный
   работающий лимит.
2. Глобальный rate limit с отдельными лимитами для `/search` и `/books/:id/content`
   (14.4.1, 14.4.4) — настройка уже зарегистрированного плагина.
3. Ограничение глубины дерева предикатов (14.4.3) — одна проверка перед компиляцией.
4. Проверка существования книги и `hideDeleted` в ручке обложек (14.3.2).
5. Заголовки в NPM плюс CSP и HSTS; грабли `Secure`-куки — в `docs/deploy.md` (14.5.2–3).
6. `/health` без подробностей о коллекции (14.3.1).
7. Чистка сессий по таймеру и отзыв при смене пароля (14.6.1–2).
8. `USER` в Dockerfile'ах, логин из лога, проверка redirect (14.6.3–5).

Пункты 1–3 закрывают обе реальные угрозы модели и делаются за один заход. Остальное —
гигиена, её можно растянуть.
