# Принятые решения

Короткие записи о том, что было выбрано и почему. Смысл файла — чтобы решение не
переоткрывалось заново: если хочется поменять что-то отсюда, сначала прочитайте, какой
альтернативе оно проиграло и по какой причине.

---

## 1. Гибрид: свой API + C++-сервер FLibrary как content-service

**Альтернативы:** расширять существующий C++-сервер; написать всё своё с нуля.

Распаковка zip/7z, восстановление картинок в fb2, извлечение обложек, mobi/djvu/pdf и
внешние конвертеры уже работают в FLibrary и стоят дорого в переписывании. При этом каждая
правка API в C++ — это Qt, DI на Hypodermic и часы сборки с Conan.

Поэтому: своё — аутентификация, поиск, пользователи; чужое и работающее — файлы книг.
C++-сервер слушает только localhost, наружу не публикуется.

**Цена:** два процесса вместо одного и внутренний контракт `/Images/*`, за которым надо
следить при обновлении upstream. Он изолирован в `src/content/opds.ts`.

---

## 2. REST + OpenAPI, а не GraphQL

**Решающий довод:** поисковый запрос — рекурсивное дерево предикатов. Рекурсия во входных
типах GraphQL допустима, но union/`oneOf` для inputs в стабильной спеке нет, поэтому узел
«либо предикат, либо группа AND/OR/NOT» пришлось бы описать одним раздутым input-типом с
рантайм-валидацией «ровно один вариант». JSON Schema описывает это точно.

Плюс: резолверы полей дают N+1 на SQLite (список из 50 книг с авторами и жанрами — это один
SQL с `GROUP_CONCAT` против 150 запросов без dataloader-ов), а бинарные ручки остаются
REST в любом случае.

Что при этом **не** теряется: HTTP-кэширование поиска. Дерево едет в теле, то есть это
`POST` и в REST-варианте.

**Путь отхода:** если понадобится обход графа, GraphQL добавляется для каталога и навигации,
а поиск остаётся на `POST /search`.

---

## 3. Две базы: коллекция read-only + свой app.db через ATTACH

**Альтернатива:** писать своё в коллекционную БД.

Схемой коллекции владеет FLibrary: `CollectionCleaner` умеет пересобирать FTS-индексы,
миграции меняют структуру, переимпорт inpx пересоздаёт файл. Всё наше там было бы снесено.

`ATTACH` вместо отдельного соединения — чтобы JOIN между своим и коллекционным оставался
одним SQL-запросом.

**Как обеспечена гарантия:** URI-имена (`file:...?mode=ro`) в better-sqlite3 не включены,
поэтому per-attach read-only через них не получить. Вместо этого READONLY открывается всё
соединение — флаг распространяется и на присоединённые файлы. Проверено: запись в `coll.*`
падает с «attempt to write a readonly database».

Отсюда следствие: процессу, который читает коллекцию и пишет своё (индексатор), нужны
**два** соединения. Первая версия индексатора этого не делала, и в момент `reindex`
коллекция становилась изменяемой — поймано тестом.

## 4. Keyset-пагинация вместо LIMIT/OFFSET

На сотнях тысяч строк `OFFSET` заставляет SQLite пройти все пропускаемые строки. Курсор —
значение ключа сортировки последней строки плюс `BookID` для однозначности, в base64url.

Следствие: ключ сортировки обязан быть NOT NULL и сравнимым, поэтому все выражения
сортировки обёрнуты в `IFNULL`.

**Дополнение: `offset` рядом с курсором.** Интерфейс показывает постраничную навигацию с
номерами страниц, а курсором в произвольную страницу не попасть — поэтому в контракте есть
и `offset`. Цена померена через API на реальной коллекции (665 тысяч книг в выдаче, без
фильтров, сортировка по названию): первая страница — 470 мс, после пропуска 200 тысяч —
1,2 с, последняя — 2,5 с. Отсюда и решение: `offset` ограничен сверху (`MAX_OFFSET`), а
курсор остаётся основным способом листать последовательно — он не дорожает с номером
страницы.

## 5. Собственный поисковый индекс в app.db

FTS-таблицы коллекции созданы FLibrary с дефолтным токенизатором `unicode61`: морфологии
нет («города» не находит «город»), индексы разнесены по четырём таблицам, `bm25()`
недоступен при компаундах.

Подробности устройства — `packages/api/src/indexer/README.md`.

**Внешний движок (Meilisearch и т.п.) не берём** пока: FTS5 на сотнях тысяч записей
справляется (замеры в README индексатора), а поиск спрятан за своим контрактом — движок
можно подменить без изменений в клиенте.

---

## 6. Свой стеммер, и в индексе обе формы слова

**Альтернатива:** библиотека; только основы в индексе.

Свой — потому что один и тот же код нужен при индексации и при разборе запроса, без нативных
зависимостей; алгоритм Snowball стандартный и хорошо специфицирован.

Обе формы — потому что Snowball на фамилиях несогласован: «иванов» → «иван», но «иванова» →
«иванов». По одним основам «Иванов» не находил бы «Иванову», а автор — основная ось поиска.
Индексируются и основа, и исходная форма, запрос собирается как `("основа" OR "форма")`.

**Цена:** примерно вдвое больше токенов на русском тексте и небольшая потеря точности. Для
каталога размен верный: потерять книгу из-за падежа хуже, чем показать лишнюю.

---

## 7. Сессия в httpOnly-куке, а не чистый HTTP Basic

Требование было «базовая аутентификация без регистрации», и в C++-сервере это HTTP Basic с
одной парой логин/пароль. Для SPA Basic плох: пароль летит в каждом запросе, нет выхода,
плохо дружит с клиентским роутингом.

Поэтому вход один раз (`POST /auth/login`) → кука сессии; пользователи заводятся CLI.
Для OPDS-читалок Basic остаётся, но его обслуживает C++-сервер, а не мы.

---

## 8. Два валидатора Ajv

Path- и query-параметры всегда приходят строками, их нужно приводить к типам. В теле
приведение вредно: `"5"` вместо `5` в дереве предикатов должно быть ошибкой, а не молча
исправляться. Один общий валидатор с `coerceTypes: false` ломал `/books/:id` — поймано
тестом.

---

## 9. Генератор фикстур вместо реальной коллекции

Реальная библиотека — десятки гигабайт, в облачной сессии её нет. Схема выгружается из
FLibrary скриптом (`pnpm fixtures:schema`), а не переписывается руками, поэтому фикстуры
совпадают с настоящей БД вплоть до деталей: `Ext` с точкой, `SearchTitle` в uppercase,
версия схемы `13` в `Settings`, позиционные коды жанров при пустом `GenreTitle`.

Расхождение фикстур с реальными данными стоит дороже, чем кажется: пока фикстуры
заполняли `GenreTitle`, тесты зелёными проходили мимо того, что в интерфейс уезжает
код жанра вместо названия.

## 10. Фасеты: не сужают сами себя, топ-N, кэш в app.db

**Альтернативы:** считать счётчики по тому же фильтру, что и выдачу; отдавать все
значения; считать заново на каждый запрос.

Счётчик по полю, которое уже отфильтровано, бесполезен: выбрав язык «ru», пользователь
увидел бы в фасете языков одно значение и не смог бы добавить «en». Поэтому при подсчёте
фасета предикаты по его собственному полю из фильтра снимаются. Снимаются только прямые
потомки верхнего `and`: внутри `or` или `not` предикат участвует в логике, и его удаление
дало бы не расширенное, а другое множество — такой фасет честно считается по полному
фильтру.

Отсюда следствие: у фасетов может быть разное множество книг, а значит, отдельные запросы.
Совпадающие множества материализуются во временную таблицу один раз на все свои фасеты —
вместе со скалярными признаками (язык, формат, год, рейтинг), так что четыре фасета из
семи дальше вообще не обращаются к коллекции. Замер на 50 000 книг, шесть фасетов:
322 мс подзапросом в каждом против 36 + 133 мс через общую таблицу.

`CROSS JOIN` в спеках фасетов — не декартово произведение, а фиксация порядка соединения:
о размере временной таблицы планировщик ничего не знает и без подсказки сканирует всю
коллекцию (замер: 72 мс против 32 мс на трёх фасетах).

Топ-20 значений вместо всех — потому что авторов и серий в выдаче тысячи. Уже выбранные
значения закрепляются в начале списка: иначе выбранный автор с тремя книгами выпал бы из
топа и снять фильтр в интерфейсе было бы нечем. Обрезание не замалчиваем: `truncated`.

Кэш — таблица `query_cache` в app.db, ключ включает отпечаток файла коллекции (mtime и
размер), поэтому обновление коллекции обесценивает кэш само собой. TTL нужен для того,
чего в ключе нет: пользовательские данные меняются, а SQL при этом тот же.

Счётчики живут в **своей операции** `POST /search/facets`, а не в ответе поиска. Причина
та же, из-за которой они дороги: считаются они по всему совпавшему множеству, то есть от
страницы и сортировки не зависят. Пока они были частью `POST /search`, выдача ждала панель
уточнения, а листание пересчитывало неизменные цифры. Туда же уехал и `total` — он такого
же порядка работа и кэшируется тем же ключом; в `/search` остался флаг `withTotal`,
выключенный по умолчанию, для клиента, которому нужен ровно один запрос.

**Цена:** счётчики могут отставать на TTL (по умолчанию 5 минут).

## 11. C++-сервер в контейнере — из официального релиза, headless — через weston

**Альтернативы:** собирать `opds` из исходников в образе; подложить QPA-плагин `offscreen` из
пакетов дистрибутива; принести бинарник в образ руками.

Сборка из исходников — это Qt 6.10+ и зависимости Conan, часы на каждое обновление. При этом
в релизах upstream уже лежит `FLibrary-<версия>-portable-Linux.tar.xz`, а в нём `opds`,
Qt 6.11 и `7z.so` — образ получается из `curl | tar`.

Дальше выясняется, что headless этот бинарник просто так не запускается: он линкует Qt Gui,
без платформенного плагина не стартует, а в сборке есть только `xcb` (нерабочий — нет
`libQt6XcbQpa`) и `wayland`. Плагин `offscreen` из пакетов дистрибутива Qt не берёт:
QPA-плагины грузятся только при совпадении major.minor («Ignoring QPA plugin due to mismatching
Qt versions»), в Ubuntu 6.10 против 6.11 в сборке. Поэтому в образе weston с
headless-бэкендом: GPU и устройства ввода ему не нужны, а `wayland`-плагин в сборке штатный.

Отсюда же база образа Ubuntu 26.04: релиз собран gcc 16, нужен `GLIBCXX_3.4.35`, в 24.04
такого libstdc++ нет.

**Цена:** зависимость от того, что upstream продолжит публиковать портативные сборки, и
weston в образе. `FLIBRARY_VERSION` в `.env` позволяет и откатиться, и обновиться.

## 12. Одна раскладка: Linux + Docker, библиотека — каталог с хоста, read-only

**Альтернативы:** держать библиотеку на SMB-шаре (NAS, машина с десктопным FLibrary)
оверрейдом к compose; один каталог на всю библиотеку; именованные тома для `app.db` и кэша;
именованный том с `driver_opts: type=none,o=bind` вместо прямого bind-mount'а.

**Сетевого хранилища нет намеренно.** SMB-раскладка у нас была, и стоила она дороже, чем
давала: SQLite берёт fcntl-блокировки даже на чтение, через CIFS они превращаются в
серверные byte-range locks — без `nobrl` это `SQLITE_BUSY`/`SQLITE_IOERR`, с ним просто
медленно; поиск делает много случайных чтений `collection.db`, а они по сети — больное
место; лечилось это копией коллекции на локальный том, то есть третьим compose-файлом и
обязанностью обновлять копию после каждого обновления коллекции. Плюс cifs-utils на хосте,
пароль от шары в `.env` и явный `vers`, потому что автонеговорка с частью NAS выбирает SMB1.
Поддерживаемый сценарий один: коллекция, архивы и данные приложения — на дисках той же
Linux-машины, где работает Docker. Библиотека на NAS — это `rsync` до неё, а не CIFS в
рантайме.

**База и архивы — разными путями (`COLLECTION_PATH` и `LIBRARY_PATH`).** Сначала здесь был
один каталог `/library` с именами внутри (`COLLECTION_FILE`, `ARCHIVES_SUBDIR`): файл
коллекции ссылается на папки, зарегистрированные в ней при импорте, и разъезжаться им
незачем. На практике незачем оказалось не всегда: у архивов и базы разные требования к
диску. Восемьсот архивов — это сотни гигабайт, их держат на большом медленном хранилище
(в нашем случае — том с NAS, примонтированный на хосте), а поиск делает много случайных
чтений `collection.db`, и ей нужен локальный SSD. Одна переменная это не выражает, а
подгонка через подкаталоги (`LIBRARY_PATH=/srv`, `COLLECTION_FILE=flibrary/collection/…`)
даёт `.env`, который через месяц не читается. Лежат вместе — обе переменные указывают
на один каталог, это и есть дефолт в `.env.example`.

**`app.db` и кэш обложек — тоже каталоги с хоста, а не именованные тома.** Том прячет
единственный невосстановимый файл в `/var/lib/docker/volumes`: бэкап превращается во
временный контейнер с `tar`, перенос раскладки — в такой же контейнер с `cp`, а
существующий `app.db` при переезде на compose молча не подхватывается — сервис поднимается
с пустой базой и «куда делись пользователи». Bind-mount делает всё это обычными файловыми
операциями. Кэш обложек — за компанию, чтобы места на диске занимали предсказуемые
каталоги. Тома остались там, где терять нечего: `caddy-data` и `caddy-config`.

**Прямой bind-mount, а не именованный том с bind-драйвером.** Индирекция через том
существовала ровно затем, чтобы оверрейд мог подменить его определение; без SMB она только
вредит — именованный том запоминает `device` при создании, и правка `LIBRARY_PATH` в `.env`
молча не действует, пока том не удалить руками. Длинный синтаксис с
`create_host_path: false` — чтобы опечатка в пути падала явно, а не создавала пустой каталог
от root.

**Read-only** — не только из-за инварианта «в коллекцию не пишем»: `opds` при старте создаёт
представление `Books_View_Opds`, то есть по своей воле пишет в коллекцию, и ro-монтирование —
способ это запретить. Проверено: `/Images/*` (обложки и файлы книг — всё, что мы проксируем)
на read-only коллекции работают, ценой отключается OPDS-каталог самого C++-сервера.

**Цена:** OPDS для читалок в дефолтной конфигурации не работает; если он нужен — `read_only`
у `opds` снимается осознанно (см. `docs/deploy.md`). Библиотеку, лежащую на другой машине,
раскладка не поднимет — её нужно сначала перенести.

## 13. Свой ограничитель запросов к content-service, а не «сколько попросили, столько и шлём»

**Симптом:** на странице книги не появлялась обложка, а скачивание файла падало по таймауту.

**Причина в C++-сервере.** Каждый его обработчик — это `QtConcurrent::run`, то есть задача
в глобальном QThreadPool размером с число ядер. Обработчик обложки (`Server.cpp`,
`RouteGetBook`) вдобавок блокирует свой поток вложенным `QEventLoop`, пока
AnnotationController не распакует архив и не разберёт книгу. Всё, что в пул не поместилось,
стоит в очереди **без ответа** — для клиента это неотличимо от зависшего сервера.

Страница выдачи просит до сотни обложек разом, а у undici число соединений на origin по
умолчанию не ограничено. Пул на той стороне забивался, и следующий запрос — скачивание —
ждал, пока освободится поток, то есть до нашего `headersTimeout`.

**Решение:** свой `Pool` с фиксированным числом соединений (`CONTENT_SERVICE_CONCURRENCY`,
по умолчанию 4) плюс ограничитель с резервом: обложек в полёте не больше `limit - 1`, и в
очереди файл встаёт перед обложками. Очередь держим у себя, потому что своя — приоритетная,
а из чужой скачивание уже не вытащить. Обложка ждёт слот не дольше 5 секунд: лучше
заглушка, чем висящее соединение.

**Альтернативы:** увеличить пул в C++ (это правка upstream и сборка с Qt); ретраи (лечат
симптом и добавляют нагрузки тому, кто и так перегружен).

Очередь ждёт **до** отправки запроса, а не после, и это принципиально: `opds` падает по
segfault, когда клиент обрывает соединение на середине выдачи (см. заметки ниже). Поэтому
не дождавшаяся слота обложка отвечает 503, ни разу не постучавшись, а таймауты самих
запросов оставлены щедрыми — обрывать уже начатую выдачу мы не хотим.

**Цена:** при живом сервере параллелизм ниже возможного. Ради этого и сделано — сервер
устроен так, что от лишнего параллелизма ему только хуже.

**Побочно закрыто:** отрицательный результат («обложки нет») больше не кэшируется по
ошибке сервера. Маркер `.missing` не протухает, поэтому один 5xx прятал обложку навсегда —
до ручной чистки кэша.

## Особенности данных FLibrary, найденные опытным путём

Их дорого находить заново, поэтому они продублированы здесь и в комментариях у кода.

- `Books.Ext` хранится **с точкой** (`.fb2`), `Books.FileName` — без расширения.
  `Books_View.FileName` — это `FileName || Ext`.
- `SearchTitle` / `SearchName` — просто `UPPER()` от значения, никакой другой нормализации.
- FTS5 `MATCH` требует **неквалифицированное имя таблицы** и не работает с алиасом:
  `FROM coll.Books_Search WHERE Books_Search MATCH ?` — да, `... fts WHERE fts MATCH ?` — нет.
- Название жанра лежит в `Genres.GenreAlias` («Научная Фантастика»), а `GenreTitle` пустой
  у всех жанров (проверено на коллекции из 504 жанров). `GenreCode` — это позиционный код
  `001.001`, показывать его пользователю нечего. У корневых жанров `ParentCode` — пустая
  строка, а не `NULL`. Коды коллекции и коды FB2 — разные словари: в fb2-файлах стоит
  `sf_history`, в `Genre_List` — `001.002`, связывает их `Genres.FB2Code`.
- `Unknown author` — не пропуск данных, а обычная запись справочника `Authors` (в нашей
  коллекции 887 книг; есть и вариант `Unknown`). Наружу такое имя не показываем: API
  подменяет его на «Неизвестный автор» — и в выдаче, и в фасете авторов, иначе одна и та
  же сущность подписана в интерфейсе двумя разными способами.
- Названия может не быть вовсе (`Title` пустой — в нашей коллекции у 19 книг из 705 тысяч).
  Интерфейс в этом случае показывает `ID: <BookID>`.
- Версия схемы коллекции лежит в `Settings` под `SettingID = 0` (это значение enum
  `IDatabaseUser::Key::DatabaseVersion`), актуальная — `13`.
- `Groups_List_User` ссылается не только на книги: `ObjectID` может быть автором, серией или
  ключевым словом — разворачивает это представление `Groups_List_User_View`.
- Связки (`Author_List`, `Series_List`, `Keyword_List`, `Genre_List`) отдают `BookID` на
  каждое совпадение: у книги два автора на «ив» — и она попадает в множество дважды.
  Поэтому множество совпавших книг дедуплицируется (`SELECT DISTINCT`), иначе получаются
  дубли в выдаче, завышенный `total` и завышенные счётчики фасетов. Уникальные индексы
  по (BookID, ключ) при этом гарантируют, что на дедуплицированном множестве `count(*)`
  в фасете — это ровно число книг.
- В `opds` 2.6.6 аргументы `--name/--database/--archives` на **существующей** коллекции
  пересоздают её пустой (5000 книг → 0). Флаги, кстати, не те, что были в 2.5:
  `--database` и `--archives`, а не `--db-path`/`--archive-folder`. Поэтому коллекция
  регистрируется QSettings-конфигом, а сервер запускается без аргументов.
- `opds` падает по segfault, если клиент обрывает соединение на середине выдачи (30
  оборванных запросов к `/Images/covers/*` — гарантированный `segfault ... in liblogic.so`).
  Через наш api не воспроизводится: обложки он вычитывает целиком.
- Имя файла в `content-disposition` C++-сервер отдаёт percent-кодированным внутри
  `filename="..."`. Декодировать такое — эвристика Chromium, а не RFC 6266, поэтому api
  перекладывает имя в `filename*=UTF-8''…`. Если заголовка нет вовсе, имя берётся из
  коллекции: иначе браузер сохранит файл как «content» — по последнему сегменту пути.
- `/Images/covers/{id}` всегда отдаёт `Content-Type: image/jpeg` — независимо от того, что
  на самом деле лежало в книге, а вместо отсутствующей обложки возвращает **200** со своей
  PNG-заглушкой (`:/images/book.png`). Caddy перед фронтом ставит
  `X-Content-Type-Options: nosniff`, поэтому PNG под видом jpeg браузер не покажет: тип
  определяем по сигнатуре файла (`detectImageType`), а не по заголовку.
- Обработчики C++-сервера живут в глобальном QThreadPool (размер — число ядер), а обложка
  вдобавок блокирует поток вложенным `QEventLoop`, пока распаковывается архив. Отсюда
  ограничитель в `src/content/opds.ts` (решение 13).
- В C++-сервере авторизация навешена только на `/`, `/opds/*` и `/web/*`; JSON-API
  `/main/getBooks/*` и скачивание `/Images/*` открыты, а в двух ручках параметры
  подставляются в SQL конкатенацией. Отдельный PR в upstream.
