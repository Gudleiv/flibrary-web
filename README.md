# flibrary-web

Веб-каталогизатор электронной библиотеки: SPA на Vue 3 + PrimeVue 4 и API на Fastify
поверх коллекции [FLibrary](https://github.com/heimdallr/books).

Аутентификация базовая, без регистрации. Главная фича — расширенный поиск.

## Архитектура

```
браузер → Caddy → api (TypeScript/Fastify) → collection.db (SQLite, только чтение)
                                           → app.db (наше: юзеры, их данные, индексы)
                                           → flibrary-opds (C++, localhost)
                                                 обложки, файлы книг, конвертеры
```

Три принципа, из которых всё вытекает:

1. **Коллекционная БД read-only.** Её схемой владеет FLibrary: она создаётся при импорте
   inpx и меняется миграциями. Всё своё — в отдельном `app.db`, подключённом через `ATTACH`,
   так что JOIN между своим и коллекционным остаётся одним SQL-запросом. Соединение для
   чтения открыто с флагом READONLY, поэтому испортить коллекцию физически невозможно.
2. **Работу с файлами не переписываем.** Распаковка zip/7z, восстановление картинок в fb2,
   извлечение обложек, mobi/djvu/pdf, внешние конвертеры — всё это уже работает в
   C++-сервере FLibrary. Он остаётся внутренним content-service на localhost, а API его
   проксирует.
3. **Контракт — источник истины.** `packages/contract/openapi.yaml`; из него генерируются
   и TS-типы, и JSON Schema для валидации в рантайме.

Подробный разбор и обоснование решений — в [docs/architecture.md](docs/architecture.md).

## Быстрый старт

Нужен Node 22+ и pnpm 10+.

```bash
pnpm install

# 1. Контракт: TS-типы и JSON Schema из openapi.yaml
pnpm --filter @flibrary/contract build

# 2. Данные для разработки: синтетическая коллекция + zip-архивы с fb2
pnpm fixtures                              # 5 000 книг
pnpm fixtures -- --books=50000             # как в критерии готовности первой фазы
pnpm fixtures -- --books=300 --no-archives # быстро, только БД

# 3. Пользователь (регистрации в приложении нет)
cd packages/api && cp .env.example .env
pnpm --filter @flibrary/api users add user secret123

# 4. Поисковый индекс (морфология, релевантность, подстроки)
pnpm --filter @flibrary/api reindex

# 5. Запуск api (:3000) и web (:5173)
pnpm dev
```

Открыть http://localhost:5173. Vite проксирует `/api` на API, чтобы сессионная кука
(httpOnly, SameSite=Lax) работала в рамках одного origin.

Обложки и скачивание книг в такой конфигурации отдадут 502: за них отвечает C++-сервер
FLibrary. Он поднимается из официального релиза, без сборки из исходников:

```bash
apt install weston libegl1 libopengl0
scripts/opds-local.sh          # 127.0.0.1:12791 — адрес, который api берёт по умолчанию
```

Всё остальное — поиск, фильтры, карточка книги — работает на фикстурах и без него: вместо
обложек показывается заглушка, скачивание объясняет причину ошибки.

## Обложки и файлы книг

Обращаться к C++-серверу надо аккуратно: его обработчики живут в пуле потоков размером с
число ядер, а обложка вдобавок держит поток, пока распаковывается архив. Всё, что не
поместилось в пул, ждёт в очереди без ответа.

Поэтому запросы идут через ограничитель (`CONTENT_SERVICE_CONCURRENCY`, по умолчанию 4) с
резервом под скачивание: сетка обложек на странице выдачи не может занять все слоты, и файл
книги не встаёт в очередь за сотней миниатюр. Обложка, не дождавшаяся слота за 5 секунд,
отдаёт 503 и заглушку — держать соединение ради картинки незачем.

Ответы различаются по смыслу: 502 — сервера нет, 503 — перегружен, 504 — не ответил вовремя,
404 — у книги нет обложки. «Обложки нет» кэшируется на диске, ошибки сервера — нет.

## Структура

```
packages/
  contract/   OpenAPI-спека — единый источник типов и рантайм-валидации
  api/        Fastify: auth, поиск, проксирование бинарных ручек
    src/search/   компилятор дерева предикатов в параметризованный SQL
    src/db/       доступ к collection.db (ro) + app.db (rw), миграции
    src/indexer/  свой поисковый индекс: морфология, релевантность, подстроки
  web/        SPA: Vue 3 + TS + PrimeVue 4 + Pinia + TanStack Query
fixtures/     генератор синтетической коллекции по схеме FLibrary
deploy/       docker-compose, Caddyfile, Dockerfile для api, web и opds
docs/         архитектура и решения
```

## Расширенный поиск

Запрос — дерево предикатов, а не набор query-параметров: так его можно сохранить, положить
в URL и собрать в UI конструктором.

```jsonc
{
  "where": {
    "op": "and",
    "nodes": [
      { "field": "author", "op": "prefix", "value": "стругацк" },
      { "field": "year", "op": "range", "from": 1960, "to": 1990 },
      // Жанр задаётся кодом коллекции («001» — «Фантастика»), их отдаёт GET /genres.
      { "field": "genre", "op": "in", "values": ["001"], "includeChildren": true },
      { "op": "not", "node": { "field": "read", "op": "eq", "value": true } },
    ],
  },
  "sort": [{ "field": "year", "dir": "desc" }],
  "limit": 50,
}
```

Поля: текстовые (`any`, `title`, `author`, `series`, `annotation`, `keyword`), перечисления
(`lang`, `ext`, `genre`, `archive`), числовые (`year`, `libRate`, `userRate`, `size`,
`seqNumber`), идентификаторы (`authorId`, `seriesId`, `keywordId`, `groupId`) и признаки
(`favorite`, `read`, `hasAnnotation`, `hasReview`, `deleted`). Полный список — в
`openapi.yaml`.

Пагинация keyset: `LIMIT/OFFSET` на сотнях тысяч строк деградирует на глубоких страницах,
поэтому курсор — это значение ключа сортировки последней строки плюс `BookID`.

Для навигации по номерам страниц (её и показывает интерфейс) есть `offset`: курсором в
произвольную страницу не попасть. Цена известна и померена — см. решение 4 в
`docs/decisions.md`.

### Морфология, релевантность и подстроки

Собственный индекс в `app.db` (см. `packages/api/src/indexer/README.md`) снимает главные
ограничения FTS-таблиц коллекции:

- «города», «городу», «городом» находят «город» — индексируются основы слов (Snowball)
  вместе с исходными формами, поэтому и фамилии находятся в любом падеже;
- сортировка `relevance` — это настоящий `bm25()` с весами по полям (название важнее
  аннотации), когда запрос состоит из одного текстового предиката;
- `substring` ищет внутри слова через триграммный индекс: «орол» находит «Королевство».

До первой индексации приложение работает по FTS коллекции — без морфологии, но работает;
в логах при старте об этом предупреждение.

### Фасеты и общее число совпадений

`POST /search/facets` — счётчики по полям (`lang`, `ext`, `genre`, `year`, `libRate`,
`author`, `series`) и `total`. Отдельная операция, а не часть выдачи, потому что и то,
и другое считается по всему совпавшему множеству: это работа другого порядка, чем
страница результатов, и от страницы с сортировкой она не зависит.

Отсюда способ пользоваться: один запрос счётчиков на набор фильтров, а листание дёргает
только `POST /search`. Ровно так и делает интерфейс — ключ запроса счётчиков не содержит
ни страницы, ни сортировки, поэтому при листании он не меняется. Если total нужен ровно
одним запросом и без счётчиков, у `POST /search` остался флаг `withTotal` (по умолчанию
выключен — это второй полный проход по множеству).

Два свойства, которые видно в выдаче:

- **Фасет не сужает сам себя.** При подсчёте счётчиков по языку предикат по языку из
  фильтра снимается: выбрав «ru», пользователь по-прежнему видит, сколько книг в «en».
  Иначе список схлопнулся бы в одно значение и множественный выбор потерял бы смысл.
  Исключение — предикат внутри `or` или `not`: убрать его оттуда нельзя, не изменив
  смысл запроса, так что такой фасет считается по полному фильтру.
- **Отдаётся топ-20 значений** (год и рейтинг — шкалы, у них до 200), уже выбранные
  значения закрепляются в начале списка. Если значений больше, в ответе `truncated: true`.

Счётчики и `total` кэшируются в `app.db` (`query_cache`, `QUERY_CACHE_TTL_SECONDS`, по
умолчанию 5 минут): ключ включает отпечаток файла коллекции, поэтому её обновление
обесценивает кэш само собой.

Замер на фикстуре в 50 000 книг, шесть фасетов панели (одна машина, до и после
разделения операций):

| Запрос                          | Было (выдача + фасеты + total) | Стало: `/search` | Стало: `/search/facets` |
| ------------------------------- | ------------------------------ | ---------------- | ----------------------- |
| «показать всё», первая страница | 186 мс                         | 27 мс            | 142 мс, из кэша 1 мс    |
| «показать всё», листание        | 46 мс                          | 27 мс            | не запрашивается        |
| текстовый запрос                | 13 мс                          | 3 мс             | 8 мс, из кэша 1 мс      |

Смысл не в сумме, а в том, что выдача больше не ждёт счётчиков, а листание их вообще
не пересчитывает.

### Что в поиске ещё не готово

- **`hasCover`** отдаёт 400 с объяснением: наличие обложки в коллекции не хранится, FLibrary
  узнаёт о ней, только распаковав книгу, — индексатор здесь не помогает.
- **Ранжирование при составных запросах.** `bm25` доступен, только когда текстовый предикат
  один: при пересечении множеств (INTERSECT/UNION) FTS-таблица во внешнем запросе
  недоступна. В остальных случаях `relevance` даёт порядок по названию.
- **Фильтры по своим данным** (`favorite`, `read`, `userRate`) в контракте есть и работают,
  но из интерфейса убраны: ставить отметки пока негде — ручки пер-юзер данных нет, поэтому
  фильтр по ним всегда давал бы пустую выдачу.

Что сделано по скорости и что осталось — в `docs/architecture.md`, раздел 13. Коротко:
фасеты с `total` уехали в отдельную операцию, индексатор умеет доиндексацию и кэширует
стемминг; осталось вытеснение в кэше обложек и пул read-воркеров.

Что осталось по безопасности — там же, раздел 14: модель угроз (один аккаунт, доверенный
круг, задача — закрыть библиотеку от посторонних), находки аудита и порядок работ. Берёмся
за него после раздела 13 — часть пунктов закрывается теми же правками.

## Деплой

Одна Linux-машина с Docker и Compose v2 — больше на хосте ничего не нужно: и API, и SPA, и
C++-сервер собираются в образах. Библиотека (`collection.db` и архивы) лежит на дисках этой
же машины и монтируется read-only; `app.db`, кэш обложек и сертификаты Caddy — в именованных
томах там же. Сетевых хранилищ раскладка не поддерживает намеренно (`docs/decisions.md`,
решение 12).

```bash
cd deploy
cp .env.example .env && chmod 600 .env   # SESSION_SECRET, LIBRARY_PATH, домен
docker compose up -d --build

docker compose exec api node dist/cli/users.js add user 'пароль'
docker compose exec api node dist/cli/reindex.js
```

C++-сервер берётся из официальной портативной сборки релиза
[heimdallr/books](https://github.com/heimdallr/books/releases), а не собирается из исходников;
наружу он не публикуется и доступен только API. Подробности, проверка поиска и скачивания,
грабли (headless-Qt, read-only коллекция, обновление коллекции) — в
[docs/deploy.md](docs/deploy.md).
