# Индексатор

Собирает собственный поисковый индекс в `app.db`. Запуск:

```bash
pnpm --filter @flibrary/api reindex           # изменения: доиндексация, если её хватает
pnpm --filter @flibrary/api reindex --force   # собрать заново целиком
```

Запускать после обновления коллекции (импорт inpx) и по расписанию. API узнаёт о готовом
индексе сам в течение десяти секунд — перезапуск не нужен (`IndexStatus`).

## Зачем он нужен

FTS-таблицы коллекции создаёт FLibrary, и у них три ограничения, которые снимаются только
своим индексом:

1. **Нет морфологии.** Они созданы без указания токенизатора, то есть с дефолтным
   `unicode61`: «города» не находит «город». Проверяется одной строкой на фикстурах.
2. **Индексы разнесены.** Название, авторы, серия и аннотация лежат в четырёх таблицах,
   поэтому поиск «везде» был объединением четырёх запросов.
3. **Нет ранжирования.** `bm25()` требует, чтобы FTS-таблица участвовала во внешнем
   запросе; при объединении четырёх таблиц компаундами она недоступна.

## Как устроено

```sql
-- релевантность, префиксы, поиск по полям
CREATE VIRTUAL TABLE books_fts USING fts5(
    title, authors, series, keywords, annotation,
    tokenize = 'unicode61 remove_diacritics 2'
);
-- подстроки: «орол» внутри «Королевство»
CREATE VIRTUAL TABLE books_trgm USING fts5(
    title, authors, series, keywords,
    tokenize = 'trigram'
);
```

Обе таблицы поколоночные — иначе предикат по конкретному полю превращался бы в поиск по
всему (это ловится тестом).

В `books_fts` кладутся **и основы, и исходные формы** слов. Причина — в стеммере: Snowball
на фамилиях даёт несогласованный результат («иванов» → «иван», но «иванова» → «иванов»),
и по одним основам «Иванов» не находил бы «Иванову». Запрос собирается так же: каждое
слово ищется как `("основа" OR "исходная форма")`. Цена — примерно вдвое больше токенов на
русском тексте; для каталога это верный размен.

Аннотации в триграммный индекс не попадают: он вырос бы в разы, а спрос на подстроку
внутри аннотации близок к нулю. Такой запрос отдаёт 400 с объяснением.

## Атомарность и безопасность

Индекс собирается в таблицы `*_new` и переключается через `ALTER TABLE ... RENAME` в одной
транзакции — поиск во время переиндексации продолжает работать на старом индексе.

Источник и приёмник — **разные соединения**: коллекция читается через read-only соединение,
индекс пишется в `app.db` через пишущее. Если бы индексатор подключил коллекцию к пишущему
соединению, она стала бы изменяемой, и главная гарантия проекта («испортить коллекцию
физически невозможно») перестала бы держаться в этом процессе.

## Когда пересобирать и когда доиндексировать

Изменение коллекции определяется по `max(UpdateID)` и числу записей в `Books` плюс mtime и
размеру файла БД — всё это хранится в `index_state`. Если ничего не поменялось, сборка
пропускается.

Если поменялось, индексатор сначала пробует **доиндексацию**: новые книги приезжают
поставкой inpx со своим `UpdateID`, поэтому «что добавилось» — это `UpdateID` больше
прежнего максимума. Такие книги дописываются прямо в рабочие таблицы (сначала удаляются
их строки — тогда прерванный запуск можно просто повторить), полная пересборка не нужна.

Одного выросшего `UpdateID` мало: в старой части коллекции книги могли пропасть, и их
строки остались бы в индексе навсегда. Поэтому проверяется ещё и число книг до прежней
границы — совпало с тем, что было при сборке, значит старая часть цела. Не совпало —
собираем заново.

Чего доиндексация не видит: **правку существующей книги**. `UpdateID` ставит импорт, а не
редактирование, так что переименование книги в десктопе индекс не заметит. Лекарство —
`reindex --force`; это же и ответ на «а вдруг индекс разъехался».

## Замеры

Синтетическая коллекция 50 000 книг (`pnpm fixtures -- --books=50000`):

|                                  |                             |
| -------------------------------- | --------------------------- |
| полная сборка индекса            | 2,2 с (3,1 с до кэша основ) |
| доиндексация поставки в 500 книг | < 0,1 с                     |
| размер `app.db`                  | 65 МБ при коллекции 45 МБ   |
| текстовый поиск, страница выдачи | ~3 мс                       |
| «показать всё», страница выдачи  | ~27 мс                      |
| глубокая страница (offset 4950)  | ~47 мс                      |

Цифры сняты на одной машине до и после правок, сравнивать между собой их можно, с чужими
замерами — нет. Кэш основ в стеммере срезает сборку примерно на треть: словарь каталога
меньше числа слов в нём, а разбор окончаний до кэша повторялся на каждое вхождение
(на этой фикстуре — 1,2 млн вызовов).

Доиндексация экономит не только время, но и диск: полная сборка держит старый и новый
индексы одновременно, то есть пик вдвое больше итогового размера.

## Чего индексатор не делает

**`hasCover`.** Наличие обложки в коллекции не хранится: FLibrary узнаёт о ней, только
распаковав книгу. Индексатор читает БД, а не архивы, поэтому этот признак так и остаётся
неподдержанным. Чтобы его заполнить, нужен отдельный проход через content-service с
опросом каждой книги — по времени это сопоставимо с полной распаковкой библиотеки.
